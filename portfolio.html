글로벌 리전 레이턴시 개선

2025.11 – 2026.05설계 · 구현 주도DynamoDB · Redis · PostgreSQL재현 실험 코드 →
문제
해외 리전에서 쓰면 국내보다 4~5배 느리다는 피드백. 유력한 원인은 서울 리전에 묶인 DB·Redis 쓰기 왕복(1회 약 150ms)이 요청마다 여러 번 발생하는 구조.
판단
Aurora Global Database·Aurora DSQL 검토 — 쓰기는 여전히 한 리전이거나 대륙 간 미지원이고 비용도 더 높아 보류. 실시간성이 강한 데이터만 리전 로컬 쓰기로 옮기기로 결정.
해결
대화방·세션·참가자 연결 수를 DynamoDB Global Tables로, 작업 큐를 리전별 Redis로 옮기고, 실시간 메시지는 모든 리전에 발행해 각 리전에서 구독. PostgreSQL은 응답을 기다리지 않고 뒤따라 쓰게 하고(DynamoDB 실패 시 PostgreSQL로 처리), 기능 플래그로 언제든 기존 구조로 되돌릴 수 있게 함.
결과
Close API 1,673 → 327ms (-80%), Create API 2,630 → 90ms (-97%) — 해외 상황을 재현한 개발 환경에서 15회 측정. 남은 병목은 Pub/Sub fan-out.

지식그래프 기반 초개인화

2026.01 – 2026.10백엔드 설계 · 구현 · 상용 반영PostgreSQL · pgvector · LLM
문제
사용자가 여러 번 고친 표기나 자신의 분야 맥락을 번역·AI 답변이 기억하지 못함.
해결
사용자 활동에서 LLM이 사실을 추출하고, 기존 사실과 같은 대상인지·값이 바뀌었는지 LLM이 다시 판단해 같으면 누적, 바뀌면 과거 값을 닫고 새 값으로 사용자별 그래프에 저장. 번역에는 용어집·배경지식으로, AI 답변에는 질문과 의미가 가까운 사실만 넣음. 모든 쌓기는 백그라운드 잡.
개선
상용 데이터를 보니 노트 발표자의 이야기가 사용자 사실로 섞이는 문제가 있어 "사용자 중심" 관계 구조로 재설계. 고정 기준선 게이트로 회귀 없이 채택한 뒤 상용 사용자 이관 완료.

LLM 프롬프트 관리 체계

2026.06설계 · 구현LangSmith
문제
프롬프트가 코드에 있어 문장 하나를 고쳐도 배포가 필요했고, 바뀐 버전의 품질을 확인할 방법이 없음.
해결
LangSmith를 원본으로 두고 서버가 직접 조회(60초 캐시, 장애 시 DB 미러 폴백). 개발/운영은 태그로 분리하고, 프롬프트를 직접 호출한 테스트 결과표를 검토해 통과한 버전만 운영 태그를 받게 함.
결과
코드 배포 없이 프롬프트를 고쳐 약 1분 안에 반영 — PO·PM용 사용 가이드를 함께 제공.

로그 · 배포 운영 안정화

2025.10 – 2026.05구축 · 장애 복구OpenSearch · Jenkins
로그
여러 리전의 서비스 로그를 OpenSearch로 수집하는 로거를 동료와 함께 구축(전송 실패가 서버에 영향 없게 설계). 이후 디스크 풀 장애는 debug 로그 유입이 원인이라 유입을 막고 보관 정책·압축·디스크 알림을 기본값으로 고정.
배포

비주얼 · 주얼리 버티컬 커머스

추천 상품 스케줄러 재구축

MySQL · MongoDB · Elasticsearch
문제
상품마다 3억 건 이상의 행동 로그에서 2주치 클릭·좋아요·장바구니 수를 세는 서브쿼리를 붙이고 주문·리뷰까지 함께 조회해 실행에 60분 이상 걸림. 가중치(클릭 5 · 좋아요 10 · 장바구니 20)도 쿼리에 고정돼 3년 넘게 손대지 못함.
해결
원본 로그 대신 동료가 만든 상품별·일별 행동 집계(MongoDB)를 읽도록 점수 계산을 다시 작성. 상품은 1,000개씩 읽고 점수는 100개씩 묶어 병렬로 계산한 뒤 Elasticsearch에 100건씩 bulk로 반영. 가중치는 쿼리에서 빼 설정값으로 분리하고, 작업이 실패하면 Slack으로 알림.
결과
스케줄러 실행 시간 60분 → 15분.

알림 메시지 워커

Redis 큐 · MongoDB
문제
100만 사용자 대상 주기 알림톡 발송이 API 서버에 부담을 줌.
해결
API 서버는 발송 작업만 Redis 큐(Bull)에 넣고, 별도 워커 서버가 500건씩 묶어 병렬 발송하고 묶음 사이에 1초 간격을 둠. 실패한 건만 모아 최대 3회 다시 보내고, 그래도 실패하면 MongoDB에 이력 저장.

Elasticsearch 스냅샷 마이그레이션 자동화

Step Functions · Lambda · S3
해결
스테이징 검색 데이터를 운영과 맞추기 위해 스냅샷 생성 → 상태 확인 → 복원 → 클러스터 확인을 Step Functions 단계로 자동화하고 EventBridge로 주기 실행.

개발 방식 · 권한

  • Feature Flag 기반 Trunk-Based 개발dev·release 브랜치를 따로 관리해 공통 코드 작업이 자주 충돌하고, 운영 배포가 늦어지면 개발 환경과 내용이 어긋남 → 팀에서 master 하나로 개발하고 기능은 플래그로 켜고 끄는 방식을 도입. 플래그는 Jira 티켓 번호를 키로 Firebase Remote Config에 개발·운영 값을 따로 두고, 꺼진 API는 문서에서 숨겨 이전 버전으로 동작. master에 병합하면 GitHub Actions가 dev·release PR을 자동 생성. 이 중 플래그 상태를 읽어 Swagger에 API별 배포 상태 라벨(운영 · 개발만 · 비활성)을 자동으로 붙이는 부분을 구현.
  • AWS 권한 정책모든 권한을 가진 단일 그룹 → 신규 입사자는 읽기 전용, 업무별 권한 그룹, 민감 작업은 별도 승인으로 분리.

윌로그 · 물류 배송 모니터링

기능 기준 서버 분리 · 통합 관제 플랫폼

NestJS · GraphQL · ECS · Lambda · InfluxDB
문제
고객사 연동 API 트래픽이 몰리면 서비스 전체가 영향을 받았고, 산업별 서비스가 따로 있어 운영 리소스가 늘어남.
해결
클라이언트 API(Core) · 디바이스 시계열(DDM) · 고객사 연동(CDL) · 알림(Noti)으로 서버를 분리. Core·DDM은 ECS, 연동·알림은 Lambda로 구성. 산업별 서비스는 출고·배송·검수·도착 공통 구조의 통합 플랫폼으로 이관.
결과
운영 중인 고객사 서비스를 멈추지 않고 배송 약 200만 건 · 디바이스 시계열 약 5억 건 이관.

문제 해결 · 협업

  • 고객사 연동 API 지연고객사가 10분마다 1만 건 이상 보내는 배송 데이터를 저장 전에 1건씩 라벨 코드 포함 검색(LIKE)으로 중복 검사해 slow query 발생(CloudWatch에서 확인) → 라벨 코드를 100개씩 묶어 한 번에 조회해 쿼리 수를 1/100로 줄이고(1만 건 기준 1만 회 → 100회), 조회 기간은 1개월에서 4일로 좁힘. 고객사·배송 정보는 메모리(Record)에 담아 다시 조회하지 않음. 실행 테스트 평균 20초 → 5초, 이후 연동 API를 Lambda로 분리.
  • 시계열 데이터 분리콤마로 이어 붙인 문자열로 저장하던 측정값(온도 · 습도 · 위치 · 측정 시간)을 InfluxDB로 분리하고, 기존 TypeORM처럼 쓰는 조회 모듈을 만들어 코드 변경을 최소화. 10분마다 들어온 측정값은 Redis Pub/Sub으로 발행하고 GraphQL Subscription이 디바이스별로 걸러 화면에 실시간 전달.
  • VOC time니즈가 정리되지 않은 고객사에 MVP를 먼저 제공하고 한 달에 한 번 현장 실무자를 만나 기능을 맞춤 개발.
